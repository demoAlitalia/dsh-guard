## 二、精度缺陷（P0，仍在发生，可直接复现）

### P0-1 读侧通配符被算成"写侧目标" ✅ 0.2.0 已修

**证据（live）**：`2026-11-10T10:21:13Z`，你拒绝了这条：

```powershell
Get-ChildItem releases\nadnet-v*.zip | Sort-Object Name | ForEach-Object { $h=(Get-FileHash $_.FullName).Hash; "{0} {1}" -f $h,$_.Name } | Set-Content releases\SHA256SUMS.txt
```

真实动作：**读多个 zip、写一个文件**。守卫判 `overwrite-mass` + `wildcard-target`，因为 `*.zip` 出现在命令里——它在读侧。

**证据（live）**：`2026-10-16T08:47:27Z`，同样被拒：

```powershell
Remove-Item 'F:\...\_tmp_asar_scan.py' -Force -ErrorAction SilentlyContinue; Get-ChildItem 'F:\...' -Filter '_tmp*' | Select-Object Name
```

`-Filter '_tmp*'` 是只读列举，却给那条**单文件删除**加上了 `wildcard-target`。

**修法**：按 `|` 切段，定位"含修改性 cmdlet 的段"，只在该段的**参数**里找通配符与多目标；读侧段只用于识别动词。预期消掉 `wildcard-target` 噪声的主要来源（65 次命中里含大量此类）。

### P0-2 代码表达式里的斜杠造出假 POSIX 路径 ✅ 0.2.0 已修

**证据（live）**：`2026-11-10T10:17—10:20` 三条被拒的打包脚本，规则都是 `external-path-target`，外部目标是 **`/stem`、`/f`**：

```python
pkg = root/"releases"/"_staging"/stem      # 被读成 posix 路径 /stem
old = root/"releases"/f"{stem}.zip"        # 被读成 /f
```

复现（当前源码）：

```
B1 Python path division + f-string → tokens ["/f"] → ask external-path-target
B2 同样意图、不用斜杠分隔       → tokens []       → allow
```

历史台账里自 2026-10-17 起仍有 **5 行**此类假目标（`/stem`、`/f`），更早还有 `/asked`、`/json|zstd/`、`</body>`、`p://127.0.0.1…`。

**修法**：POSIX 候选必须满足"斜杠前是边界 **且** 斜杠后是词字符 **且** 整段至少两级（含 `/` 后的分隔）或长度 ≥ 3，并排除紧跟 `"`、`{`、`$`、`|`、`}` 的候选；更稳的做法是只在命令是 POSIX shell 语法（`bash` 工具）时才启用 POSIX 词法，Windows 的 `pwsh` 里基本不需要它。

### P0-3 双反斜杠路径未规范化，被当成"区外" ✅ 0.2.0 已修

**证据（live）**：`2026-11-19T07:16:44Z`（今天，我写诊断脚本时）：

```
externalTargets: ["C:\\\\Users\\\\me\\\\.dsh\\\\emergency\\\\guard-audit.jsonl"]
```

脚本文本里写 `'C:\\Users\\...'`（JSON/JS 字面量的双反斜杠），守卫原样取词，不折叠重复反斜杠，于是**同一个文件**变成了"工作区外"。

复现（当前源码）：

```
doubled → inside? false，outside ["C:\\\\Users\\\\me\\\\.dsh\\\\emergency\\\\guard-audit.jsonl"]
single  → inside? true
```

台账里因此产生了 **26 条**双反斜杠目标记录，最近一条就在观测当天（`2026-11-19T07:25:05Z`）。

**修法**：`normalize()` 先折叠 `\\+` → `\`（并处理 `\\?\` 前缀）；顺带把 `%USERPROFILE%`、`$env:VAR` 这类未展开变量标记为"不可判定"，而不是当作普通路径。

> 已完成的相关修复（不在待办里）：工作区常量（3 次拒绝）、`README.md` 里的 `md` 别名、`/asked`、`</body>`、URL 的 `p://`、`format-volume` 的错误归类。

## 三、覆盖缺口（P0/P1）

### P0-4 `edit` 完全不在闸门内，而它是最高频的写操作 ✅ 0.2.0 已修（仅范围判定）

| 工具 | 35 天调用次数 | 是否受闸门约束 |
|---|---|---|
| `pwsh` | 2006 | 是 |
| **`edit`** | **1202** | **否** |
| `read` | 444 | 否（只读，合理） |
| `write` | 88 | 是 |

**风险**：`edit` 可以对工作区**之外**的文件做定向修改（例如 `C:\Users\me\.dsh\...`、另一个项目的配置文件），而守卫只看 `pwsh`/`write`。这不是理论风险——同一会话里你确实编辑过工作区外的内容。

**修法**：把 `edit` 纳入，但**只判范围、不判批量**：目标是本会话工作区内的单文件 → 放行（保持现有零摩擦）；落入 `protectedRoots` 或工作区外 → 询问。成本极低，堵住的是真实缺口。

### P1-5 `plugin_manager` 这类"装代码"的工具不受约束 ✅ 0.3.0 已修

35 天里 3 次调用。它能安装/移除插件 bundle，效果是**下次启动时执行任意代码**——比一次删除更持久。建议：`plugin_manager` 的写操作（install/remove/enable）一律 ask，理由写成"这会改变下次启动加载的代码"。

### P1-6 新增工具/宿主升级后的覆盖漂移 ✅ 0.3.0 已修（`extraGatedTools` + `untracked-tool`）

本次观测里 Node 从 v24.18.1 升到 v24.21.0、DSH 也更新过，插件毫发无损（`41e61ba5…` 未变），说明 patch 挂载方式稳。但工具清单是宿主决定的：一旦出现 `run_code` / `bash` / `str_replace_editor` 之类，当前代码**默认不管**。建议加配置项 `extraGatedTools: []`，并把"未知但声明了文件写入能力的工具"记一条 `untracked-mutation-tool` 审计（仅记录、不拦），以便升级后立刻发现漂移。

### P1-7 `working_directory` 与工作区缓存的一致性 ✅ 0.4.0 已修（读 `workingDirectory.get(session)`；相对目标按当前目录解析）

会话里出现过 1 次 `working_directory`。守卫按 `SessionHeader.cwd` 判定并**按 agent 缓存**（header 不可变）。如果该工具在工具层改了实际 cwd 而没有改 header，守卫会继续用旧根判定相对路径——这是"判定根与实际执行根不一致"的隐患。**需要一次专门验证**：调用前后各判一条相对路径命令，看 `exec.agent.session.header.cwd` 是否变化；若不变，则缓存必须改为读取工具层 cwd。

## 四、交互疲劳（P1）

### P1-8 重复询问：同一条命令被问 63 次 ✅ 0.3.0 已修（`rememberApproved`，默认关闭）

台账里 21 条**完全相同**的命令被反复询问，累计 63 次（占 133 次弹窗的 47%）。最高的一条被问 **12 次**（同一段 Python heredoc 反复执行）。

这是最大的人机成本，也是最容易改的。建议**可选**的"短时间内记住同一命令":

```json
{ "rememberApproved": { "enabled": false, "scope": "session", "ttlSeconds": 900 } }
```

规则：只在 `scope=inside` 且分类为 `mass` 的命令上生效；键 =(命令原文哈希, 工作区根, 规则集)；命中时仍写审计（`decision: "allow", rule: "remembered-approval"`），并让状态行显示"已记住 N 条"。默认关闭，开启需显式配置——安全换效率，交给使用者决定。

### P1-9 跨项目工作时"区外"判定过窄 ✅ 0.3.0 已修（`additionalRoots`）

`external-path-target` 是最高频规则（89 次）。工作区分布显示你同时在 Nad-Net / dsh / ZeroPanel 三个项目里工作，而守卫只信**当前会话的 cwd**。因此在一个项目会话里引用另一个项目（以及 `~/.dsh` 之外的公共目录）都会被判"区外"。

建议增加 `additionalRoots: []`（额外可信根，默认空）：配置后这些根视同"工作区内"。这是把现有 `protectedRoots` 的镜像机制显式化，而不是放宽判定。

### P1-10 状态行过长且每次会话都注入 ✅ 0.3.0 已修（`statusLine: "brief"`）

当前状态行约 **430 字符（≈110 token）**，每个新会话注入一条，且包含会漂移的审计计数。建议：

- 拆成 `statusLine: "full" | "brief" | false`，默认 `brief`（只报姿态 + 工作区 + 开关 + 最近一次拦截的规则名，约 120 字符）；
- 把"审计计数"从会话常驻消息移到 `status.ps1` / 状态页（那是按需查询的地方）。

## 八、不建议做的事

- **不要加"总是允许"白名单**。15 次拒绝里有 3 次是真实想拦的递归删除；一次性放行会把这些变成静默删除。P1-8 的"记住批准"限定短 TTL + 精确命令 + 仅区内批量，才不破坏这一点。
- **不要把 `deny` 放宽成 `ask`**。35 天只有 2 次 deny，且都没误伤；它是最后一道。
- **不要用文件名后缀（`.json`/`.db`）来定义"数据文件"**。你实际工作里 `releases\*.zip`、`SHA256SUMS.txt`、`RELEASE_LEDGER.md` 都是要被写的数据面；按后缀分级只会制造新的误判。
